# RHFiles — 设计文档

> 目标：用 Rust 打造一个极致性能、GUI 现代化的文件浏览器，替代 Windows 自带资源管理器和 Files 等第三方工具。

---

## 一、愿景

| 维度 | 目标 |
|------|------|
| **性能** | 50万文件目录秒开，滚动无掉帧，内存 <100MB |
| **外观** | 现代化、可深度定制主题，支持 acrylic/mica 半透明 |
| **架构** | 纯 Rust，无 GC 停顿，编译为单文件 native binary |
| **体验** | 多标签、双面板、内置预览，键盘优先操作 |

---

## 二、GUI 框架选型（需要你决定）

### 候选一：Slint（推荐 ⭐）

- **渲染**：Skia / FemtoVG / Qt 三后端可选
- **方式**：`.slint` 声明式 DSL → 编译为原生代码
- **性能**：启动 <100ms，内存极低，支持嵌入式设备
- **风格**：Material / Fluent / Cupertino，可自定义样式系统
- **异步**：需手动桥接（`slint::invoke_from_event_loop` + channel）
- **成熟度**：v1.x 稳定 API，商业支持
- **缺点**：DSL 学习曲线，复杂自定义控件需 Rust + Slint 混合

**参考项目**：Czkawka (30k stars) — 用 Slint 构建的文件去重/GUI 工具

### 候选二：Iced（纯 Rust 推荐）

- **渲染**：wgpu（GPU）/ tiny-skia（CPU 回退）
- **方式**：Elm 架构，纯 Rust 代码
- **性能**：GPU 加速，retained mode，只渲染变化部分
- **异步**：一等公民，`Command::perform(async_op, Msg::Result)`
- **成熟度**：30k stars，生态丰富但 API 仍有 break
- **缺点**：Elm 架构冗长（每操作需定义 Msg + update），无内置树控件需自建

**参考项目**：doseer — 用 Iced 构建的文件管理器

### 候选三：Tauri + 前端（Web 技术栈）

- **渲染**：系统 WebView2
- **方式**：Rust 后端 + Web 前端 (React/Vue/Solid/Svelte)
- **性能**：异步 I/O 轻松，但 WebView 体积 30-50MB，内存额外 +50MB
- **风格**：CSS 能力最强，真正"现代"外观
- **异步**：自带 async，前后端 IPC 通信
- **成熟度**：106k stars，最成熟
- **缺点**：WebView 开销大，不符合"高效"定位

**参考项目**：IYERIS — Tauri v2 文件管理器

### 候选四：egui（即时模式）

- **渲染**：wgpu / glow (OpenGL)
- **方式**：每帧重建 UI，代码极简
- **性能**：简单场景极快，但大量文件列表需手动虚拟化
- **异步**：完全手动
- **成熟度**：30k stars
- **缺点**：深层目录树极不适合即时模式

**参考项目**：SteamCloudFileManager — egui 文件管理工具

---

### 我的建议

| 如果重视... | 选 |
|-------------|-----|
| 极致性能 + 小体积 | **Slint** |
| 纯 Rust 体验 + 现代异步 | **Iced** |
| 最美观 + 最快开发 | **Tauri** |

> **我推荐 Slint**：编译到原生代码，启动速度媲美 Windows 自带资源管理器，样式系统可以做到非常现代的外观，且不需要 WebView 开销。

### 关键模块

| 模块 | 职责 | 关键技术 |
|------|------|----------|
| `rhfiles-core` | 文件系统操作、枚举、属性读取 | `std::fs`, Windows API via `windows-rs` |
| `rhfiles-thumb` | 缩略图生成与缓存 | 线程池 + 磁盘缓存，先占位后加载 |
| `rhfiles-watch` | 文件变更监听 | `notify` crate (Debounced) |
| `rhfiles-search` | 文件名实时过滤 | 二分查找/trie，子线程 FTS |
| `rhfiles-app` | GUI 层 | Slint / Iced |
| `rhfiles-config` | 配置持久化 | TOML 或 SQLite |

## 四、性能设计（核心差异化）

### 4.1 文件枚举策略

- **主路径**：`FindFirstFileEx` (via `windows-rs`) — 单次系统调用获取全量文件
- **批量渲染**：每批 100 条通知 UI 线程，不阻塞
- **懒加载属性**：先显示文件名/图标，详情属性按需异步加载

### 4.2 虚拟列表（关键）

- 目录有 100 万文件时，只渲染可视区域 + 上下缓冲各 50 行
- 行高固定，跳过测量，直接计算 offset → slice
- 滚动时复用 UI 容器，不创建/销毁节点

### 4.3 缩略图管线

- **并发池**：4-8 线程取缩略图（vs Files 的串行 Semaphore=1）
- **LRU 内存缓存**：最近 500 张缩略图常驻内存
- **磁盘缓存**：`.rhfiles_cache/` 目录，SQLite 索引
- **占位符**：先显示扩展名图标，缩略图加载完成后替换

### 4.4 异步 I/O 架构

```
           tokio runtime (multi-thread)
          ┌─────────────────────────────────┐
Main Thread│                                 │
(GUI loop) │  channel  ┌──────────────────┐  │
    │      ├──────────►│ FileEnumTask     │  │
    │      │  (send)   │ (recv+process)   │  │
    ▼      │           └────────┬─────────┘  │
  Update   │                    │ callback    │
  UI       │  channel          ▼              │
           ◄──────────┐ ThumbnailTask        │
                       │ SearchTask           │
                       │ FileOpTask           │
                       └─────────────────────┘
```

- 零阻塞主线程：所有 I/O 在 tokio 线程池执行
- 批量通知：用 `tokio::sync::mpsc` channel，一批次传递一个更新

### 4.5 文件监听

- 单个 Debounced Watcher（vs Files 的三层 watcher 链）
- 去重处理（同一文件多次事件合并）
- Git 状态异步轮询（可配置间隔）
