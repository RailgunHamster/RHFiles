# RHFiles 0.1.51

## 中文

- **修复真正的病根：7-Zip 的错误信息被我们自己的解码 bug 吞掉了**。之前读取 7-Zip 的 stderr 用的是 `read_to_string`，而 7-Zip 的控制台输出是系统 OEM 代码页（中文系统为 GBK）；只要错误信息里含一个中文路径，整段 stderr 就会 UTF-8 解码失败并整体丢弃，于是界面只能显示无用的进度尾部 `Sub items Errors: 23678`，看不到真正的原因。现在：
  - 解压时给 7-Zip 加 `-sccUTF-8`，让它以 UTF-8 输出；
  - 同时把 stderr 改为按字节读取再做有损解码，任何编码下都不会再丢信息。
  - 于是 0.1.49/0.1.50 里那句没有信息量的报错，现在会明确显示 `ERROR: Wrong password : <文件>`。
- **密码错误的提示更清楚**：重试弹窗会标注「密码错误，请重新输入」；三次尝试后仍失败时，提示改为「解压失败：密码错误，或该压缩包需要密码而未提供」，并附上 7-Zip 的原始信息。
- 新增端到端测试：明文 ZIP、ASCII 密码 ZIP、以及 **Bandizip 创建的中文密码 ZIP**（用 RHFiles 完全相同的参数解压并校验文件内容，同时验证错误密码会得到 `Wrong password`）；另有加密分卷 ZIP 的正确密码解压测试。附带发现：7-Zip 自身不允许用非 ASCII 密码**创建** ZIP（`参数错误`），但解压中文密码 ZIP 完全正常。

## English

- **Fixed the real root cause: 7-Zip's error text was being swallowed by our own decoding bug.** stderr was read with `read_to_string`, but 7-Zip writes console output in the system OEM code page (GBK on Chinese systems); a single non-UTF-8 byte anywhere in the stream made the whole read fail and return nothing, so the UI could only show the useless progress tail `Sub items Errors: 23678` instead of the actual reason. Now:
  - extraction passes `-sccUTF-8` so 7-Zip emits UTF-8;
  - stderr is read as raw bytes and decoded lossily, so no encoding can lose the message again.
  - The uninformative error from 0.1.49/0.1.50 now reads `ERROR: Wrong password : <file>`.
- **Clearer wrong-password handling**: the retry prompt says "Wrong password — please try again", and after three attempts the alert becomes "Extract failed: wrong password, or the archive needs one and none was provided" with the raw 7-Zip message attached.
- Added end-to-end tests: plain ZIP, ASCII-password ZIP, and a **Bandizip-created Chinese-password ZIP** extracted through the exact RHFiles argument vector with content verification plus a wrong-password check; also a correct-password extraction of an encrypted split ZIP. Side finding: 7-Zip itself refuses to *create* ZIPs with non-ASCII passwords (`invalid parameter`), while extracting them works fine.
