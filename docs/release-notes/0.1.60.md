# RHFiles 0.1.60

## 中文

### 预览性能（实测数据）

- **PDF 预览改为按需加载**：此前每次选中 PDF 都会立刻把内嵌 PDF 查看器挂进预览面板，而它跑在应用**同一个渲染器**里——文件一大（扫描件、几万页）就会把界面拖住。现在选中 PDF 只显示文件信息与两个按钮（「打开 PDF」「加载预览」），点「加载预览」才创建查看器。
  - 实测（真实应用 + CDP）：改动前每份 PDF 选中即触发查看器加载（观测到 67 ms 级阻塞）；改动后**选中时不再创建 iframe**（仅一次 43 ms 抖动），点击「加载预览」后才创建 ✓。
- **大 HTML 的实测结论**：后端本来就把文本预览限制在 65 KB（`system.rs` 的 `read_file_text(&p, 65_536)`），前端再截断一次。实测 **64 MB 的 HTML 预览耗时 75 ms、零卡顿**。所以"HTML 大了会卡"在 0.1.60 上复现不出来；如果你手上有仍然卡顿的具体文件，把路径给我，我用同样方式直接测它。

### 「网页用 RHFiles 选择」的排查工具

- 这条链路（伴随选择器 → 让 Windows 对话框跳转 / 回传文件）的每一步现在都能单独验证，新增跳转诊断：
  ```powershell
  $env:RHFILES_TEST_NAVIGATE_TO='C:\Windows'
  cargo test -p rhfiles-tauri --lib navigates_an_open_file_dialog -- --ignored --nocapture
  ```
  会打印对话框跳转**前/请求/后**的文件夹，跳错即断言失败——可直接判断是"写进去的路径错了"还是"对话框最终落在别处"。
- 顺带确认过的一项：应用发布给选择器的位置列表与各标签页**实际路径完全一致**（用 CDP 对比过 9 个标签页），所以不是列表本身错位。

### 关于"为什么不能在开发机上验证"

本开发机是**无输入桌面的会话**，实测：`GetForegroundWindow()` 恒为 0、`SetForegroundWindow` 恒失败、文件对话框对 UI Automation 暴露 **0 个**控件（枚举 `#32770` 类窗口得到 0）。而这条链路的每一步（前台切换、Ctrl+L、Ctrl+V、回车、UIA 写入）恰好全都依赖这些能力。所以：

- **能验证的**（已用真实应用 + CDP 验证）：界面布局、图标、预览渲染与耗时、231 项内置测试套件、位置列表内容。
- **不能验证的**：宿主对话框的真实交互。这类只能在你那台有桌面的机器上用上面的诊断命令跑一次，输出就是结论。

## English

### Preview performance (measured)

- **PDF previews now load on demand.** Selecting a PDF used to mount the embedded PDF viewer immediately, and that viewer runs inside the app's **own renderer**, so a large or scanned document dragged the whole UI down. Selection now shows the file information plus two buttons ("Open PDF", "Load preview"); the viewer is created only when you ask for it.
  - Measured in the live app over CDP: before the change each selected PDF started the viewer (67 ms-class stall observed); after it, **no iframe is created on selection** (a single 43 ms blip) and the iframe appears only after pressing "Load preview".
- **Large HTML, measured:** the backend already bounds text previews to 65 KB (`read_file_text(&p, 65_536)` in `system.rs`) and the UI truncates again. A **64 MB HTML previews in 75 ms with no stall**, so "large HTML is slow" is not reproducible on 0.1.60 — send me the exact file if one still lags and I will measure that one the same way.

### Tooling for "choosing files with RHFiles from a browser page"

- Every step of that chain (companion picker → make the Windows dialog jump / hand files back) can now be verified on its own; a navigation diagnostic was added:
  ```powershell
  $env:RHFILES_TEST_NAVIGATE_TO='C:\Windows'
  cargo test -p rhfiles-tauri --lib navigates_an_open_file_dialog -- --ignored --nocapture
  ```
  It prints the dialog's folder **before / requested / after** and fails the assertion when it lands elsewhere, which separates "the written path was wrong" from "the dialog ended up somewhere else".
- Also confirmed: the location list the app publishes to the picker matches the real tab paths exactly (compared all 9 tabs over CDP), so the list itself is not the problem.

### Why this development machine cannot verify it

This machine is a session **without an input desktop**. Measured: `GetForegroundWindow()` is always 0, `SetForegroundWindow` always fails, and the file dialog exposes **zero** UI Automation children (enumerating `#32770` windows returns 0). Every step of that chain — foreground transition, Ctrl+L, Ctrl+V, Enter, UIA writes — depends on exactly those capabilities. Therefore:

- **Verifiable here** (and verified with the live app over CDP): layout, icons, preview rendering and timings, the 231-test in-app suite, the published location list.
- **Not verifiable here**: interaction with the host dialog. That needs one run of the diagnostics above on a machine with a desktop; the output is the answer.
