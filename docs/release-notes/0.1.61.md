## 中文

### 1. PDF 预览：改回直接加载，但不在选择路径上启动（实测）

上一版改成"点击才加载"不合你的要求，本版改回**直接加载**，但把查看器的创建挪出选择处理函数：先更新信息面板，再在下一帧（`requestAnimationFrame` + `setTimeout(0)`）挂载查看器。

真实应用 + CDP 实测（1.56 MB PDF）：

| 指标 | 结果 |
| --- | --- |
| 选择处理函数耗时 | **1 ms**（不阻塞） |
| 查看器是否自动加载 | **是**（无需点击） |
| 观测到的卡顿 | 1 次 67 ms（查看器自身绘制，已移出交互路径） |

说明：查看器运行在应用**同一个渲染器**内，它的初始化开销无法完全消除（除非把预览放到独立 webview，可作后续项）；这次改动保证的是**点击、选择、面板刷新都不再被它拖住**。

### 2. 「跳转进了文件夹而不是选中文件」——找到根因并修复

你的现象（`...\Pictures` 跳进了 `...\Pictures\FireShot`，而且没选中任何文件）指向了投递链路里的一个兜底逻辑：

- 交付文件时先尝试把路径写入对话框的**文件名框**。此前只查找自动化 ID **1148**（新版 `IFileDialog`），而 **Chromium 的文件选择器用的是旧式 `GetOpenFileName` 对话框，文件名框 ID 是 1152** → 查找失败。
- 查找失败后，代码退回到「**地址栏粘贴 + 回车**」。那是给"跳转文件夹"用的动作：把文件路径粘到地址栏再回车，对话框只会**打开该文件所在目录**并（在浏览器上传对话框里）什么都不选中——**却仍然返回成功**。这正好解释了"跳进了 FireShot 但没选中文件"。

修复内容：

1. 文件名框同时支持 **1148 与 1152**（并兜底取对话框内第一个编辑框）；
2. **交付文件时彻底移除地址栏粘贴兜底**——那条路只会导航、不会选中；
3. 写入后**读回文件名框校验**，不一致就报错（错误信息会带上框里实际内容）；
4. 配合 0.1.59 的"确认后必须关闭对话框"校验，这条链路上再没有"看起来成功其实没生效"的分支。
5. 新增单元测试覆盖两代控件 ID 与"文件夹路径不算有效交付"。

因此如果仍不成功，你会看到**明确的原因**（例如"对话框没有保留所选文件（文件名框显示 …）"），而不是静默地跳进一个目录。

## English

### 1. PDF preview: automatic again, but never started inside the selection path (measured)

The on-demand version did not match what you asked for, so the viewer loads automatically again — but it is created *after* the information panel has painted, in the next frame (`requestAnimationFrame` + `setTimeout(0)`).

Measured in the live app over CDP (1.56 MB PDF):

| Metric | Result |
| --- | --- |
| Selection handler | **1 ms** (does not block) |
| Viewer loads automatically | **Yes** (no click needed) |
| Observed stall | one 67 ms blip (the viewer's own paint, moved off the interaction path) |

Note: the viewer runs inside the app's **own renderer**, so its initialisation cost cannot be removed entirely (isolating it in a separate webview would be a follow-up); what this change guarantees is that clicking, selecting and the panel update are never blocked by it.

### 2. "It jumped into a folder instead of taking my file" — root cause found and fixed

Your description (`...\Pictures` jumping into `...\Pictures\FireShot`, with nothing selected) pointed straight at a fallback in the hand-off:

- Delivering files first writes the paths into the dialog's **File-name** field. It only looked for automation id **1148** (the modern `IFileDialog`), while **Chromium's picker still uses the legacy `GetOpenFileName` dialog whose File-name field is 1152** — so the lookup failed.
- It then fell back to "**paste into the address bar + Enter**". That is the *navigation* gesture: pasting a file path there makes the dialog **open the containing folder** and select nothing (and in a browser upload dialog, upload nothing) — **while still reporting success**. That is exactly "it jumped into FireShot but took no file".

Fixes:

1. The File-name field is now looked up by **1148 and 1152** (with the dialog's first edit control as a last resort);
2. The address-bar paste fallback is **removed from file delivery** — it can only navigate, never select;
3. The field is **read back** after writing; a mismatch fails with the field's actual contents in the message;
4. Together with 0.1.59's "the dialog must actually close", no branch of this chain can look successful without having worked.
5. Added unit tests covering both generations' control ids and that a folder path is not a valid delivery.

If it still fails, you will now see a concrete reason (for example "the browser dialog did not keep the selected files (its file-name field shows …)") instead of silently jumping into a folder.
