# RHFiles 0.1.59

## 中文

- **修「选好了之后浏览器对话框没有任何反应」**。投递链路此前有两处依赖前台窗口的脆弱环节：
  - 确认动作是靠 `SendInput` 发送 `End / 空格 / 退格 / 回车` 完成的。而 Windows 的**前台锁定**经常让 `SetForegroundWindow` 失败；更关键的是，用 UIA 写入文件名框**不会把键盘焦点移到该输入框**，于是这些按键会落到对话框里当前有焦点的控件（通常是文件列表），回车自然什么也不做——而 RHFiles 却认为投递成功、关闭确认栏并提示"已送回"，用户看到的就是"没效果"。
  - 现在确认改为**全程 UI Automation**：直接 Invoke 对话框的默认按钮（通用对话框的按钮自动化 ID 为 `1`，与系统语言无关；另有"非取消按钮中优先匹配与标题同名者"的兜底），**不需要前台、不需要模拟按键**。仅在 UIA 无法驱动时，才退回键盘路径。
- **不再假装成功**：投递后现在会**等待并确认对话框真的关闭**（唯一的可信信号）。对话框仍然开着就返回错误，确认栏会显示具体原因，而不是静默地关闭并提示成功。
- 因此这次改动的副作用是：如果仍然失败，你会看到明确的原因（`Unable to confirm the selected files` 等），而不是"没效果"。
- 新增一个按需运行的诊断测试 `delivers_into_an_open_edge_upload_picker`（默认忽略）：对**已经打开的**文件对话框逐步打印投递链路每一步的结果（识别结果、写入后的文件名框内容、确认是否被接受、对话框是否关闭），用于在没有前台钩子的会话里排查这条链路。用法见 `docs/DEBUGGING.md`。
- 说明：本机（无交互桌面的会话）无法完成真实投递验证——Win32 对话框在没有桌面时连 UIA 内容都不完整（只能取到系统菜单项），`SetForegroundWindow` 恒定失败。因此这项修复需要在有桌面的机器上由你实测确认。

## English

- **Fixed "nothing happens in the browser dialog after pressing Use these files".** The hand-off had two fragile dependencies on the foreground window:
  - confirmation was performed by `SendInput`-ing `End / Space / Backspace / Enter`. Windows' foreground lock frequently refuses `SetForegroundWindow`, and — more importantly — writing the field through UI Automation never moves keyboard focus into it, so those keys land on whatever control does have focus (usually the file list). Enter then does nothing, while RHFiles reported success, closed the bar and claimed the files had been sent: exactly the "no effect" symptom.
  - Confirmation is now **pure UI Automation**: the dialog's default button is invoked directly (the Common Item Dialog exposes it as automation id `1`, which is language independent, with a fallback that prefers the enabled non-cancel button labelled like the dialog). No foreground window and no synthetic keystrokes are needed; the keyboard path remains only as a fallback for dialogs UI Automation cannot drive.
- **No more pretending**: the hand-off now waits for and verifies that the dialog actually closed — the only trustworthy success signal. If it is still open, the command fails and the bar shows the reason instead of silently reporting success.
- Consequence of the above: if it still fails, you will now see a concrete reason (`Unable to confirm the selected files`, etc.) rather than "no effect".
- Added an opt-in diagnostic test `delivers_into_an_open_edge_upload_picker` (ignored by default) that prints each step of the hand-off against an **already open** file dialog: recognition, the File-name field contents after writing, whether the confirmation was accepted, and whether the dialog closed. See `docs/DEBUGGING.md`.
- Note: a real hand-off could not be verified on this machine (a session with no interactive desktop): a Win32 dialog does not expose its full UI Automation tree there (only its system menu), and `SetForegroundWindow` always fails. This fix therefore needs your confirmation on a machine with a desktop.
